## 1. 목표·범위
### IN
1. `draftToRecipe` 순수함수 — draft → 생산앱 recipes 부분 문서(§6.6 매핑). + 테스트

## 3. 구현 단위

### 3-1. `src/features/recipes/draftToRecipe.ts` (신규, 순수)
§6.6 매핑표 그대로. Firebase 의존 없음(Timestamp/serverTimestamp는 mutation에서).
```ts
export type RecipeIngredientRow = {
  id: string; name: string; baseWeightG: number; unitName: 'g' | 'kg'
  isProductionUnit: boolean; sortOrder: number
  autoDeductInventory: boolean; linkedToInventory: boolean
}
export type DraftRecipePayload = {
  name: string; displayName: string
  target: string            // species 매핑 (호두님 확정값)
  category: string          // 기본 'raw'
  active: boolean           // 항상 false
  version: number           // 1
  sortOrder: number         // 0
  ingredients: RecipeIngredientRow[]
  unitPresets: number[]     // []
  source: 'recipesss'; recipesssDraftId: string
  createdBy: string
}
export function draftToRecipe(
  draft: RecipeDraft, ingredients: IngredientMap, ownerUid: string,
): DraftRecipePayload
```
- **영양제 제외**: `ingredients[row.ingredientId]?.kind === 'ingredient'` 인 행만.
- 각 행: `{ id: row.ingredientId, name: ing.name, baseWeightG: row.weight, unitName: row.unit, isProductionUnit: row.ingredientId === draft.unitIngredientId, sortOrder: row.sortOrder, autoDeductInventory:false, linkedToInventory:false }`.
- `target` = speciesToTarget(draft.species) — **호두님 확정 매핑** 적용.
- `createdAt`/`updatedAt`는 payload에 **넣지 않음**(mutation에서 serverTimestamp).
- 테스트: 영양제 제외, isProductionUnit 표시, baseWeightG/unitName 매핑, target/category/active 값.

### 3-2. `recipeMutations.ts` — `useRegisterRecipe(uid)`
```ts
// recipes/{id} create + draft.registeredRecipeId/registeredAt (batch)
import { collection, doc, serverTimestamp, writeBatch } from 'firebase/firestore'
mutationFn({ draft, payload }):
  const ref = doc(collection(db, 'recipes'))          // auto id 선발급
  const batch = writeBatch(db)
  batch.set(ref, { ...payload, createdAt: serverTimestamp(), updatedAt: serverTimestamp() })
  batch.update(draftRef(uid, draft.id), { registeredRecipeId: ref.id, registeredAt: Date.now() })
  await batch.commit(); return ref.id
  invalidate ['recipeDrafts', uid]
```
- ⚠️ **create-only**: `batch.set(ref, ...)`는 신규 ref라 항상 create. 기존 문서 건드리지 않음.
- payload에 undefined 필드 없도록(생산 전용 필드는 아예 생략 — Firestore undefined 거부).

### 3-3. 등록 UI — `RecipeDetailPage.tsx`

- 성공 토스트/메시지 + 버튼 상태 갱신.

### 3-4. 코드 타입 정리

### 3-5. (조건부) `firestore.rules` — recipesss-create 전용 최소 규칙
**선결조건 1에서 권한 없을 때만.** `match /recipes/{recipeId}` 블록에 추가:
```
// recipesss: 자기가 만드는 문서만 create (기존 write=isProductionWriter는 유지)
allow create: if signedIn()
  && request.resource.data.source == 'recipesss'
  && request.resource.data.createdBy == request.auth.uid;
```
- update/delete는 **넓히지 않음**(create만). 기존 문서 보호 유지.
- ⚠️ deploy는 호두님(DL-033/036). 단일 정본이라 이 파일에만.
- 보안: signed-in 누구나 source='recipesss'로 create 가능 → 내부 신뢰 범위라 허용. 더 좁히려면 `request.auth.uid == '<호두uid>'`로 제한(호두님 결정).

## 아키텍트 노트
- **공유 컬렉션 오염 방지가 최우선.** 매핑 추정으로 push 금지 — §0 2건 확정 후.
- 생산앱은 ingredients를 **denormalize(인라인 id+name+baseWeightG)** 로 저장 → recipesss ingredientId/name 그대로 인라인 OK(생산 ingredient 마스터와 id 매칭 불필요). 단 `meatTypeId`(재고 연결)는 recipesss가 모르므로 생략 → 호두님이 생산앱에서 연결.
- `active:false`로 들어가야 생산앱에서 미완성 레시피로 인지하고 호두님이 보완 후 활성화. 절대 active:true로 push하지 말 것.
