## 0. 전제·맥락

- 호두님이 추가한 원료 병합(`71d5f20`)의 정합성 구멍을 잠그는 작업이다. **순수함수(`buildIngredientMergePlan`)·타입·테스트는 Claude가 이미 수정·커밋(`a637364`, DL-034)** 했다. 이 지시서는 **그 위에 배선·UI만** 얹는다.
- 이미 끝난 것(다시 만들지 말 것):
  - `buildIngredientMergePlan`이 이제 `presets?` 입력을 받고 `changedPresets`·`summedDraftIds`를 반환한다. `draft.unitIngredientId` 치환·중복행 합산·`mergeReviewPending` 플래그까지 순수함수에서 처리됨.
  - `RecipeDraft.mergeReviewPending?: boolean` 타입 추가됨.
- **네가 할 일 = 이 출력을 실제로 쓰는 것**: ①프리셋을 로드해 플랜에 넘기고 `changedPresets`를 batch write, ②병합 모달에 경고 2종, ③`mergeReviewPending` draft에 확인(붉은) 버튼.

## 1. 목표·범위

### IN (이번에 구현)
1. `IngredientsPage`에서 프리셋 로드 → `buildIngredientMergePlan({ ..., presets })`에 전달
2. `useMergeIngredients`가 `changedPresets`도 batch write + `['recipesssPresets']` invalidate
3. 병합 모달 경고 2종 (등록 레시피 드리프트 / 버려지는 영양값)
4. `/recipes` 목록에서 `mergeReviewPending` draft에 **붉은 "합산 확인" 버튼** → 클릭 시 플래그 해제(mutation)

### OUT (이번에 만들지 말 것)
- ❌ 프리셋 재설계(v2 회귀·자동코드) — 별도 후속 지시서
- ❌ 등록된 `recipes/*` 자동 재푸시 — DL-025대로 deferred (경고만)
- ❌ duplicate 영양값 자동 승계 — 이번엔 경고만 (호두님 결정: 경고 추가까지)
- ❌ 병합 순수함수 로직 변경 — 이미 완료. `ingredientMerge.ts`·`.test.ts` 건드리지 말 것

## 3. 구현 단위

### 3-1. 프리셋 배선 — `IngredientsPage.tsx`
- `usePresets(uid)` 호출(이미 있는 훅). `const presets = presetsQuery.data ?? []`.
- `handleMerge`의 `buildIngredientMergePlan({ ... })` 호출에 `presets` 추가.
- ⚠️ `mutationPending` 분기(L82 부근)에 `presetsQuery` 로딩/`mergeIngredients` 상태 영향 없게 기존 패턴만 따를 것. 새 로딩 상태 추가 불필요(presets는 모달 경고·플랜용일 뿐).

### 3-2. 프리셋 write — `ingredientMutations.ts` `useMergeIngredients`
- `mutationFn` 입력 타입에 `changedPresets: Preset[]` 추가.
- batch에 추가: `for (const preset of changedPresets) batch.set(presetRef(uid, preset.id), preset)`.
  - `presetRef(uid, id) = doc(db, \`recipesssPresets/${uid}/items\`, id)` — 경로는 `presetQueries.ts`의 컬렉션 경로와 **반드시 일치**시킬 것(확인 후 사용).
- `onSuccess`에 `void queryClient.invalidateQueries({ queryKey: ['recipesssPresets'] })` 추가.
- ⚠️ `plan` 전체를 `mutateAsync(plan)`로 넘기므로 `summedDraftIds`도 페이로드에 섞여 들어온다. mutationFn에서 **필요한 필드만 구조분해**(`target, deleteIds, changedDrafts, changedPresets`)하면 됨.

### 3-3. 모달 경고 2종 — `MergeIngredientModal` (`IngredientsPage.tsx` L582 부근)
모달은 이미 선택된 원료 목록(`ingredients`, 첫 번째 = target)을 받는다. 추가 props로 계산해 표시:

**경고 A — 버려지는 영양값(#5)**: duplicates(= 선택 원료 중 target 제외) 가운데 `nutrientProfile`에 키가 ≥1개 있거나 `source`가 있는 것들. 있으면:
> ⚠️ 다음 원료의 입력된 영양값/출처가 삭제됩니다: {이름들}. 병합 후 target 원료에 다시 입력해야 합니다.

**경고 B — 등록 레시피 드리프트(#4)**: 선택 원료(duplicate ids)를 composition에 포함하면서 `registeredRecipeId`가 있는 draft 목록. 계산엔 `drafts`가 필요하므로 모달에 `drafts`(또는 미리 계산한 `affectedRegistered: {name}[]`) prop 전달. 있으면:
> ⚠️ 등록된 레시피 N건은 재푸시 전까지 옛 원료를 유지합니다(자동 반영 안 됨): {레시피명들}.

- 두 경고 모두 **차단(blocking) 아님** — 노란/주황 배너로 표시하고 병합 버튼은 그대로 동작. (호두님 결정: 경고만)
- 빈 경우 배너 미표시.

### 3-4. 확인(붉은) 버튼 — `/recipes` 목록
- draft 행에 `draft.mergeReviewPending === true`면 **붉은 "합산 확인" 버튼/뱃지** 표시. (DL-034: 호두님이 합산 결과를 확인하는 게이트.)
- 클릭 → `mergeReviewPending`을 지우는 mutation: `recipeDrafts/{uid}/items/{id}`에 `setDoc(..., { merge: true })` 또는 전체 객체에서 플래그 false/삭제 후 `setDoc`. **기존 필드 보존 필수**(전체 객체 다시 쓸 거면 draft 그대로 + `mergeReviewPending` 제거). `['recipeDrafts']` invalidate.
  - 새 훅 `useClearMergeReview(uid)`를 `recipes`쪽 mutations 파일(없으면 신규 `recipeMutations.ts`)에 추가하거나, 간단히 `IngredientsPage`의 `useUpdateIngredient`처럼 `setDoc(draftRef, { ...draft, mergeReviewPending: false })` 패턴 사용.
- ⚠️ "사용 게이트"의 강도: 이번엔 **시각적 경고 + 한 번 클릭으로 해제**까지만. 실제로 편집/등록을 *막는* 하드 게이트는 레시피 편집 화면(1-D)·프리셋 재설계 때 함께. 지금 `/recipes`는 조회 위주라 붉은 버튼+해제로 충분.
